### 1-2. 요구사항 3가지 반영

**① 찾을 문자열 여러 개 추가**
- `SearchConfig.secondaryTexts: List<String>` — 추가/삭제 제한 없음.
- `matchAll` 토글: 기본 **OR**(하나라도 발견 시 알림), 켜면 **AND**(전부 발견해야 알림).
- AND 판정은 한 라운드 안에서 스크롤 스텝마다 매칭 결과를 **누적**한다.
  (지연 로딩 페이지에서 문자열이 서로 다른 스크롤 위치에 나타나도 판정되게 하기 위함)

**② 다른 앱 위에 떠서 백그라운드로 계속 동작**
- `SYSTEM_ALERT_WINDOW` + `TYPE_APPLICATION_OVERLAY` 기반 오버레이 윈도우.
- `OverlayService` = `foregroundServiceType="dataSync"` Foreground Service + `PARTIAL_WAKE_LOCK`.
- Activity 는 설정 화면일 뿐. Activity 가 죽어도 탐색은 계속된다.

**③ 1cm 원형 플로팅 버블로 축소 + 버블 뒤에서 탐색 계속**
- 버블 지름 = `DisplayMetrics.xdpi / 2.54` 로 런타임 계산 (xdpi·ydpi 평균, 비정상 시 densityDpi → 60dp 폴백).
- 축소 시 **WebView 를 파괴하지 않는다.** 윈도우 크기를 유지한 채
  `alpha = 0.01f` + `FLAG_NOT_TOUCHABLE` + `FLAG_NOT_FOCUSABLE` 적용.
- 버블: 드래그 이동 / 가장자리 스냅 애니메이션 / 롱프레스 시 하단 종료 영역 표시 / 탭하면 확장.

### 1-3. 탐색 동작

```
루프 (사용자가 중지할 때까지 무한 반복)
 1. URL 로드                       (타임아웃 30초)
 2. 1차 문자열 탐색 → 없으면 스크롤하며 계속 → 발견 시 해당 요소 클릭
 3. 클릭 후 DOM/URL 변화 대기 → 맨 위로 → 스크롤 1스텝씩 내리며 2차 문자열 목록 탐색
 4. 발견 → 즉시 알림 → 루프 일시정지 ([계속] 누르면 재개)
 5. 페이지 끝까지 미발견 → 새로고침 → 대기(기본 5초) → 2번으로 복귀
```

- WebView + JavaScript 인젝션으로 DOM 텍스트 탐색·클릭·스크롤 수행.
- **JS `alert()` 사용 안 함.** 페이지가 띄우는 alert/confirm/beforeunload 는 `WebChromeClient` 가 자동 confirm 처리해 블로킹을 막는다.
- same-origin iframe 순회 포함, cross-origin 은 try/catch 로 무시하고 개수만 로그에 남긴다.
- 무한스크롤: 바닥에서 `scrollHeight` 가 **3회 연속** 변하지 않으면 바닥으로 판정.
- 문자열 매칭: 공백(NBSP·제로폭·BOM 포함) 접기 + 소문자화 후 비교.
- 각 단계 타임아웃(JS 15초 / 로드 30초). 실패해도 루프가 죽지 않고 다음 사이클로 넘어간다.
  루프 전체 예외는 5초 백오프 후 자동 재기동.
- 새로고침 최소 간격 5초 강제 (서버 부담 방지).

### 1-4. 알림 (각각 on/off)

| 채널 | 설정 키 | 동작 |
|---|---|---|
| 시스템 알림 | `notifySystem` | IMPORTANCE_HIGH 채널, [계속]/[정지] 액션 포함 |
| 진동 | `notifyVibrate` | 1초 × 3회 패턴 |
| 사운드 | `notifySound` | 기본 알림음 |
| 오버레이 배너 | `notifyBanner` | 화면 상단 오버레이 배너 + WebView 안 하이라이트/배너 |
| 버블 색상·뱃지 | `notifyBubble` | 버블 빨강 전환 + 누적 발견 횟수 뱃지 |
| 스크린샷 | `notifyScreenshot` | `filesDir/shots/found_yyyyMMdd_HHmmss.png` 저장 |

발견 이력은 `filesDir/found_log.txt` 에도 탭 구분으로 누적된다.

### 1-5. 플로팅 오버레이 윈도우 구성

| 윈도우 | 내용 | 플래그 |
|---|---|---|
| webWindow | WebView 전용. 항상 붙어 있고 크기가 바뀌지 않는다 | 확장: 포커스 가능 / 축소: `NOT_TOUCHABLE`+`NOT_FOCUSABLE`, alpha 0.01 |
| controlWindow | 하단 컨트롤 바 (시작·정지·계속·축소·설정·종료) | `NOT_FOCUSABLE` |
| bubbleWindow | 원형 버블 (약 1cm) | `NOT_FOCUSABLE`+`LAYOUT_NO_LIMITS` |
| bannerWindow | 발견 배너 (계속·정지·닫기) | `NOT_FOCUSABLE` |
| closeWindow | 드래그/롱프레스 시 하단 종료 영역 | `NOT_FOCUSABLE`+`NOT_TOUCHABLE` |

컨트롤 바를 WebView 와 같은 윈도우에 넣지 않은 이유: 같은 윈도우면 컨트롤 바를 숨길 때 WebView 높이가 바뀌어
페이지가 리플로우되고 스크롤 위치가 흐트러진다. 윈도우를 분리하면 WebView 뷰포트가 절대 바뀌지 않는다.

### 1-6. 상태 복원

- 설정은 전부 DataStore 에 저장(입력 후 400ms 디바운스 자동 저장).
- `was_running` 플래그 저장 → `START_STICKY` 로 프로세스가 재시작되면 이전 탐색을 자동 복원.
- Activity 는 `configChanges` 지정으로 회전 시 재생성되지 않으며, 어차피 루프는 서비스가 들고 있어 회전과 무관.
- 버블 좌표도 DataStore 에 저장 → 재시작 시 같은 자리에 복원.

### 1-7. 권한 처리

`SYSTEM_ALERT_WINDOW` / `POST_NOTIFICATIONS` / `FOREGROUND_SERVICE(+DATA_SYNC)` / `WAKE_LOCK` / `VIBRATE` /
`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`.

- 첫 화면 상단에 권한 카드가 있고, 각 항목에서 해당 설정 화면 인텐트로 바로 이동한다.
- 미허용 상태여도 **크래시 없이** 안내만 뜬다.
  (`Settings.canDrawOverlays` false → 오버레이 창을 만들지 않고 로그만 남김,
   `POST_NOTIFICATIONS` 없으면 `SecurityException` 을 삼킴, 설정 인텐트 실패 시 앱 정보 화면으로 폴백)
- **AccessibilityService 는 사용하지 않는다.**

## 5. 실기기 검증 및 버그 수정 (2026-08-06 오후)

Galaxy Z Fold (**SM-F966N**, Android 15, 1080x2520, 420dpi) 실기기에 설치해 검증했다.

### 5-1. 발견한 버그 — 오버레이 컨트롤 바 재부착 시 터치 무반응

**증상**
확장 패널의 버튼(시작/축소/설정/종료)이 **첫 확장에서는 정상 동작**하지만,
한 번 축소했다가 버블을 탭해 다시 확장하면 **모든 버튼이 무반응**이 된다.
화면에는 정상적으로 그려지고, 크래시나 예외 로그도 전혀 남지 않는다.

**원인 규명 과정**
- `dumpsys window windows` 로 z-순서 확인 → 컨트롤 바 창(#9)이 WebView 창(#11) **위에 정상 배치**되어 있었다.
  즉 터치는 컨트롤 바 창까지 도달하고 있었고, z-순서 문제가 아니었다.
- 두 창 모두 `mHasSurface=true isReadyForDisplay()=true` → 렌더링도 정상.
- 결론: `ComposeView` 인스턴스를 `WindowManager.removeView()` 후 다시 `addView()` 로
  **다른 윈도우에 재사용**하면 그리기는 되지만 포인터 입력이 라우팅되지 않는다.

**수정**
`ViewCompositionStrategy.DisposeOnLifecycleDestroyed` 로 컴포지션을 유지한 채 뷰를 재사용하던 방식을 버리고,
표시할 때마다 `ComposeView` 를 **새로 생성**하고 숨길 때 참조를 버리도록 변경했다.
(`OverlayManager.newComposeView()` 신설, 컨트롤 바 · 발견 배너 · 종료 영역 3곳에 적용)

```
수정 파일: app/src/main/java/com/why2korea/bgsearch/overlay/OverlayManager.kt
백업:      _backup/OverlayManager.20260806.v1.kt
```

### 5-3. 아직 확인하지 못한 항목

## 8. v2.1.0 — 3차 문자열 / 줄 클릭 / 실제 새로고침 (2026-08-06)

요청 3가지를 반영했다.

### 8-1. 새로고침이 "반드시" 되게

기존에는 당겨서 새로고침 제스처를 **보내기만** 하고 성공으로 쳤다.
제스처를 받아주지 않는 화면에서는 아무 일도 안 일어난 채 다음 라운드로 넘어갔다.

이제 `ScanService.refreshPage()` 가 **새로고침이 실제로 일어났는지 확인**한다.

```
1) 화면에서 명시적 새로고침 컨트롤을 찾아 클릭
   (새로고침 / 새로 고침 / refresh / reload / 다시 시도 / 다시시도 / 재시도)
   → 반영 확인되면 성공
2) 당겨서 새로고침 제스처 (화면 18% → 82%, 700ms 느린 드래그)
   → 반영 확인되면 성공
3) 위 흐름을 엔진이 한 번 더 재시도
4) 그래도 확인 안 되면 뒤로가기로 이전 화면 복귀 → 1차 문자열 클릭부터 재시작
   (목록→상세 구조에서는 이게 사실상 재조회다)
```

**반영 확인 방법** — 새로고침이 일어나면 화면이 잠깐 비었다가 다시 채워진다.
트리거 직후 250ms 간격으로 화면을 관찰해
`내용 해시가 달라짐` 또는 `노드 수가 절반 이하로 떨어짐` 중 하나가 잡히면 새로고침으로 판정한다.
(단순히 새로고침 전후 내용을 비교하면, 내용이 같은 페이지에서 항상 실패로 오판한다)

5회 연속 확인 실패하면 경고 알림을 보낸다. 루프는 계속된다.

### 8-2. 3차 문자열 — 같은 줄에서 추가 확인

2차 문자열이 발견된 **그 줄 안에** 3차 문자열까지 있어야 발견으로 친다.
3차 문자열 목록이 비어 있으면 이 검사를 하지 않는다. (선택 기능)

예) 2차 `09일` + 3차 `예약가능` → "09일" 이 있는 줄에 "예약가능" 도 있어야 알림

**"줄" 판정** — 2차 문자열을 가진 가장 안쪽 노드에서 조상을 타고 올라가며,
조건(2차 + 3차)을 모두 만족하는 **가장 작은 조상**을 줄로 본다.

조상 높이가 **화면 높이의 30% 이하**일 때만 줄로 인정한다.
이 제한이 없으면 3차 문자열이 화면 아무 데나 있어도 최상위 컨테이너가 둘 다 포함한다는
이유로 같은 줄로 오인한다.

2차 문자열의 OR/AND 토글도 **한 줄 안에서** 판정하는 의미로 바뀌었다.
- OR: 한 줄에 2차 문자열이 하나라도
- AND: 한 줄에 2차 문자열이 전부

### 8-3. 발견한 줄을 클릭한 뒤 알림

조건을 만족하는 줄을 찾으면 **그 줄을 한 번 클릭한 뒤** 알림을 띄운다.

```
줄 발견 → 줄 클릭 (ACTION_CLICK → 실패 시 좌표 탭) → 1.2초 대기
       → 스크린샷 → 알림/배너/진동/뱃지 → 일시정지
```

클릭으로 화면이 바뀌므로 스크린샷은 **클릭 결과 화면**이 찍힌다.
설정에서 `발견한 줄을 클릭한 뒤 알림` 을 끄면 클릭 없이 알림만 한다.

발견 배너·알림·`found_log.txt` 에 **줄 전체 텍스트**가 함께 기록된다.

### 8-4. 추가된 설정

| 설정 | 기본값 | 설명 |
|---|---|---|
| 3차 문자열 목록 | 비어 있음 | 같은 줄에서 추가 확인할 문자열 (OR 매칭) |
| 발견한 줄을 클릭한 뒤 알림 | 켬 | 끄면 클릭 없이 알림만 |
| 새로고침 실패 시 뒤로가기로 복귀 | 켬 | 끄면 새로고침 실패해도 그대로 다음 라운드 |

### 8-5. 검증 상태

`assembleDebug` / `assembleRelease` BUILD SUCCESSFUL.

**v2.1.0 에서 새로 들어온 것은 실기기 미검증이다.** (테스트 직전 USB 분리)
- 3차 문자열 같은 줄 판정 (양성·음성 모두)
- 줄 클릭 → 알림 순서
- 새로고침 반영 확인 및 뒤로가기 폴백

## 10. v2.2.0 — 클릭 미반영 / 발견 후 자동 정지 (2026-08-06)

사용자 검증 피드백 2건을 반영하고, 그 과정에서 클릭 대상 오선택 1건을 추가로 잡았다.

### 10-1. [수정] 1차 문자열 클릭이 화면에 반영되지 않던 문제

**증상** — 로그에는 `1차 클릭 성공 [ACTION_CLICK]` 이 찍히는데 실제 화면에서는
아무 일도 일어나지 않았다.

**원인** — `ACTION_CLICK` 은 접근성 노드에 액션을 전달했다는 뜻일 뿐,
웹 콘텐츠에서는 true 를 돌려주고도 실제 클릭 핸들러가 동작하지 않는 경우가 있다.

**수정** — 클릭을 쏜 뒤 **화면이 실제로 바뀌었는지 확인**하고, 안 바뀌었으면 다른 방식으로 재시도한다.

```
1) 노드가 화면 밖이면 ACTION_SHOW_ON_SCREEN 으로 먼저 끌어온다
2) ACTION_CLICK  → 1.2초 안에 화면 변화 확인 → 성공
3) 좌표 탭 제스처 → 1.2초 안에 화면 변화 확인 → 성공
4) 둘 다 변화 없으면 clicked=false, 엔진이 같은 자리에서 최대 3회 재시도
```

설정에 **[1차 클릭에 좌표 탭 우선 사용]** 토글을 추가했다.
`ACTION_CLICK` 이 계속 헛도는 화면에서는 이걸 켜면 처음부터 사람 손가락과 같은 방식으로 누른다.

### 10-2. [수정] 클릭 대상을 브라우저 주소창에서 골랐다

**증상** — 위키백과에서 1차 문자열 `평택` 을 찾으랬더니 본문 링크가 아니라
크롬 **주소창**("ko.wikipedia.org/wiki/평택시")을 클릭했다. 그 다음 라운드에서는
공유 시트("웹페이지 링크를 공유합니다")를 눌렀다.

**원인** — 브라우저 툴바도 같은 앱 창의 노드다. 주소창 텍스트에도 `평택` 이 들어 있는데,
기존 로직은 "먼저 발견한 보이는 노드"를 그냥 골랐다.

**수정** — 후보를 전부 모은 뒤 **자기 텍스트가 가장 짧은 노드**를 고른다.
(보이는 노드에 큰 가산점) 주소창 텍스트는 링크 라벨보다 훨씬 길어서 자연히 걸러진다.

수정 후: `1차 클릭 성공 [gesture-tap] "평택" - 화면 변화 확인됨`

### 10-3. [추가] 1차 클릭 후 2차 탐색까지 대기시간을 설정에서 조절

`고급 설정 > 1차 클릭 후 2차 탐색까지 대기 (ms)`, 기본 **2000ms**.
기존에는 1500ms 하드코딩이었다. 클릭한 화면이 다 뜨기 전에 2차 스캔이 시작되던 문제를 사용자가 조절할 수 있다.

### 10-4. [추가] 문자열을 최종 발견하면 재검색 자동 정지

`stopWhenFound` 설정 추가, **기본 켬**.

- **켬(기본)** — 발견 → 알림·배너·진동·스크린샷 → 즉시 루프 정지.
  알림과 배너는 지우지 않고 그대로 남긴다. 배너 버튼이 `[다시 시작] [닫기]` 로 바뀐다.
- **끔** — 기존 동작. 발견 시 일시정지만 하고 `[계속]` 을 누르면 이어서 탐색한다.

### 10-5. 실기기 검증 (SM-F966N, 위키백과 페이지)

한 사이클 전체가 로그로 확인됐다.

```

줄 발견: [10일] · "이다. 1995년 5월 10일,"
줄 클릭 성공 [gesture-tap]
발견! 10일
스크린샷 저장: found_20260806_180517.png
발견했으므로 재검색을 정지합니다.
탐색 정지: 발견 후 자동 정지
```

버튼이 `[다시 시작] [닫기]` 로 바뀌며 버블이 빨강 + 뱃지 1 로 전환되는 것까지 확인했다.

## 11. v2.3.x — 뒤로가기 제거 / 새로고침 / 로딩 대기 (2026-08-06)

사용자 검증 피드백: "못 찾으면 새로고침만 하랬는데 왜 이전 페이지로 돌아가나",
"새로고침이 안 돼서 계속 평택 탭에 머문다", "새로고침 전 5초 쉬고, 그 시간을 설정에서 조절하게".

대상 사이트(해군복지포탈 잔여티 페이지)에서 직접 검증하며 수정했다.

### 11-1. [제거] 새로고침 실패 시 뒤로가기 폴백

새로고침이 확인되지 않으면 뒤로가기로 복귀하던 폴백이 있었다.
브라우저에서 이걸 하면 **대상 페이지 자체를 벗어난다.** 요구사항은 "못 찾으면 새로고침만" 이므로
폴백을 완전히 제거했다. 설정(`backOnRefreshFail`)도 삭제했다.

실패해도 페이지를 그대로 둔 채 최대 3회까지 새로고침만 재시도하고, 다음 라운드로 넘어간다.

브라우저 오버플로 메뉴 경로에서도 위험이 있었다. 메뉴 버튼을 눌렀는데 메뉴가 안 열린 상태에서
BACK 을 누르면 페이지가 뒤로 간다. **메뉴가 실제로 열린 것을 확인한 경우에만** BACK 으로 닫도록 고쳤다.

### 11-2. [추가] 새로고침 전 대기시간 (설정 가능)

`고급 설정 > 못 찾았을 때 새로고침 전 대기 (ms)` — 기본 **5000ms**.
문자열을 못 찾은 뒤 바로 새로고침하지 않고 쉬었다가 진행한다.

### 11-3. [수정] 클릭 성공 판정 기준이 틀렸다

`ACTION_CLICK` 후 화면이 바뀌어야 성공으로 봤는데, **클릭이 정상으로 들어가도 결과가 비어
화면이 그대로인 페이지가 있다.** (잔여티가 없으면 목록이 비어 화면이 안 바뀐다)
이 때문에 멀쩡한 클릭을 실패로 오판하고 같은 자리에서 무한 재시도했다.

판정을 둘로 분리했다.
- `clicked` = 클릭 동작이 실제로 전달됐는가 (성공 판정)
- `changed` = 그 결과 화면이 바뀌었는가 (참고 정보, 로그에만 표시)

접근성 트리 덤프로 확인한 실제 구조 — 클릭은 처음부터 정상 동작하고 있었다.

```
<node class="android.view.View" content-desc="평택(만포대)" clickable="true" focused="true" ...>
  <node class="android.widget.TextView" text="평택(만포대)" clickable="false" ... />
```

### 11-4. [추가] 클릭 결과가 채워질 때까지 대기

이게 "2차 문자열을 못 찾는" 진짜 원인이었다.

이 페이지는 지역을 선택하면 잔여티 목록을 **AJAX 로 뒤늦게** 불러온다.
(페이지 안내에도 `※10초 경과 후에도 뜨지않으면 잔여티가 없는 것 입니다`)
기존에는 클릭 후 2초만 기다리고 스캔해서, 아직 빈 화면을 보고
"미발견 + 바닥 도달" 로 잘못 판정했다.

`awaitContentGrow()` 를 추가해 클릭 전 화면과 비교하며 내용이 실제로 채워질 때까지 기다린다.
채워진 뒤에도 계속 늘어나는 중일 수 있으므로 노드 수가 안정될 때까지 조금 더 기다린다.

같은 이유로 라운드 시작 시 1차 문자열이 나타날 때까지 기다리는 `awaitTextAppear()` 도 추가했다.

새 설정: `1차 문자열 등장 대기 (최대 ms)` — 기본 **25000ms**.

### 11-5. 실기기 검증 결과

| 항목 | 결과 |
|---|---|
| 뒤로가기로 페이지 이탈 | **없음** (로그·화면 모두 확인) |
| 새로고침 동작 | `새로고침 확인됨 [pull-to-refresh]` 반복 성공, 초기 화면 복귀 확인 |
| 새로고침 전 5초 대기 | `2차 문자열 미발견 - 5.0초 쉬었다가 새로고침` |
| 1차 문자열 등장 대기 | `1차 문자열 등장 확인` |
| **1차 클릭** | **정상 동작 확인** — 화면에 잔여티 목록 155행이 실제로 로드된 것을 접근성 덤프로 확인 |

### 11-6. 확인하지 못한 것

- **2차 문자열 발견 → 줄 클릭 → 알림 경로를 이 사이트에서 확인하지 못했다.**
  검증 중 목록이 15초 안에 안 뜨는 경우가 있어 스캔이 빈 화면을 봤다.
  기본 대기를 25초로 올렸지만, 실제로 발견까지 이어지는지는 확인하지 못했다.
- 3차 문자열 같은 줄 판정
- 목록이 길 때의 스크롤 동작 (크롬은 화면 밖 행도 접근성 노드로 노출하므로
  스크롤 없이도 읽히지만, 가상 스크롤을 쓰는 페이지에서는 다를 수 있다)

## 12. v2.4.1 — 라운드를 새로고침으로 시작 / 클릭 대상 오선택 수정 (2026-08-06)

### 12-1. [수정] 1차 문자열 클릭이 엉뚱한 노드에 나가고 있었다

v2.2.0 에서 "후보 중 텍스트가 가장 짧은 노드를 고른다" 규칙을 넣었는데,

```
3) 자기 텍스트가 짧은 노드      (주소창처럼 긴 텍스트에 우연히 포함된 것 제외)
```

### 12-4. 실기기 전체 경로 검증 (대상 사이트)

## 13. v2.5.0 — 새로고침 과다 / 페이지 이탈 수정 (2026-08-06)

사용자 피드백: "짧은 시간에 새로고침을 너무 많이 한다", "페이지를 벗어나 '예약하기' 로 나온다".

### 13-1. [원인] 새로고침이 수십 번 일어난 이유

`refreshPage()` 가 당겨서 새로고침 전에 `scrollToTop()` 을 부르는데,
이 함수는 스크롤이 안 되면 **아래로 쓸어내리는 제스처**로 대체한다.
크롬에서 화면 맨 위에서의 아래로 쓸기는 **그 자체가 pull-to-refresh** 다.
최대 30회 반복하므로 짧은 시간에 새로고침이 수십 번 일어났다.

**수정** — `scrollToTopNoGesture()` 신설. 새로고침 직전 위치 조정은
`ACTION_SCROLL_BACKWARD` 만 쓰고 제스처는 절대 쓰지 않는다. (최대 10회)

### 13-2. [원인] 페이지를 벗어난 이유

`refreshViaBrowserMenu()` 가 "메뉴 / 더보기" 라벨을 가진 노드를 찾아 눌렀는데,
이게 **사이트 자체의 햄버거(☰) 메뉴**를 눌러 다른 페이지로 넘어가 버렸다.

**수정** — 브라우저 메뉴 경로를 **완전히 제거**했다.
화면의 새로고침 컨트롤을 찾아 누르는 경로도 함께 제거했다.
이제 새로고침 수단은 **당겨서 새로고침 하나뿐**이다. 클릭할 대상이 없으니 페이지를 벗어날 수 없다.

제거된 것: `refreshViaBrowserMenu()`, `findNodeByLabels()`, `MENU_LABELS`,
`BROWSER_PACKAGES`, `REFRESH_LABELS`, `currentPackage()`

### 13-3. [변경] 새로고침 시도 2회로 제한

`REFRESH_ATTEMPTS = 2`. 라운드당 당겨서 새로고침은 최대 2번만 나간다.
(실측: 정상 동작 시 라운드당 1회)

### 13-4. [개선] 클릭 결과 대기를 조건 충족 시 즉시 종료

고정 대기 대신, 조건에 맞는 줄이 보이면 즉시 다음 단계로 넘어간다.
`awaitContentGrow()` 대신 `findRowAndClick(doClick=false)` 를 700ms 간격으로 폴링한다.

### 13-5. 실기기 검증

```
새로고침 확인됨 [pull-to-refresh]        ← 라운드당 1회
1차 문자열 등장 확인
1차 클릭 [ACTION_CLICK] "평택(만포대)"
대기시간 안에 조건에 맞는 줄이 없음 - 스캔으로 확인
줄 발견: [09일] + [06시] · "08월 09일 a코스 18홀 06시 00분"
줄 클릭 성공 [ACTION_CLICK]
발견! 09일, 06시 → 스크린샷 → 발견 후 자동 정지
```

- **새로고침 총 1회** (기존에는 수십 회)
- **페이지 이탈 없음** — 잔여티예약 목록 화면 그대로 유지
- 발견 배너에 `[줄] 08월 09일 A코스 18홀 06시 00분` 정확히 표시

### 13-6. 대상 페이지 동작 메모 (사용자 설명 반영)

- 최초에 **잔여티예약** 페이지를 띄워둔 상태에서 시작한다.
- 새로고침하면 하단 지역 탭이 **포항(충무대)** 로 선택된 상태로 돌아온다.
- 그래서 1차 문자열을 `평택` 으로 두어 **평택(만포대)** 탭을 클릭하게 한다.
- 평택 목록은 클릭 후 **약 30초** 뒤에 채워진다. 그래서 라운드가 약 40초 걸린다.
  `1차 문자열 등장 대기` 를 35000 이상으로 두면 로그가 더 깔끔해진다.

## 14. v2.5.1 — 새로고침 폭주 완전 차단 (2026-08-06)

v2.5.0 에서 고쳤다고 했는데 **여전히 순식간에 20회 이상 새로고침이 일어났다.**

### 14-1. [원인] 제거했다고 생각한 호출이 그대로 남아 있었다

v2.5.0 에서 `scrollToTopNoGesture()` 를 새로 만들어 넣었지만,
**그 위에 있던 기존 `scrollToTop(30)` 호출을 지우지 않았다.**

```kotlin
override suspend fun refreshPage(waitMs: Long) ... {
    scrollToTop(30)          // ← 남아 있던 호출. 아래로 쓸기 최대 30회 = 새로고침 20+회
    delay(300)
    scrollToTopNoGesture()   // ← 새로 넣은 것
    ...
}
```

`scrollToTop` 은 `ACTION_SCROLL_BACKWARD` 가 실패하면 아래로 쓸기로 대체하는데,
크롬에서 맨 위에서의 아래로 쓸기는 그 자체가 pull-to-refresh 다.

### 14-2. 수정

1. `refreshPage` 에서 `scrollToTop(30)` 호출 삭제
2. `scrollToTop` 자체에서 **아래로 쓸기 폴백을 완전히 제거** —
   이제 `ACTION_SCROLL_BACKWARD` 만 쓰고, 실패하면 즉시 반환한다. 반복 횟수도 10회로 제한.
3. **최소 간격 안전장치** — `MIN_PULL_INTERVAL_MS = 5000`.
   어떤 경로로 연달아 호출돼도 5초 안에는 두 번 나가지 않는다.
4. **발사 횟수 로그** — 제스처를 쏠 때마다 `pull-to-refresh #N` 을 남긴다.
   이제 실제 횟수를 로그로 바로 셀 수 있다.

### 14-3. 아래로 쓸기 호출 지점 (전수 확인)

소스 전체에서 아래로 쓸어내리는 제스처는 **`refreshPage` 안의 한 줄이 전부**다.

```

```
